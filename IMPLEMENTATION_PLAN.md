# План реализации MVP сервиса для учителей и репетиторов

## Назначение документа

Этот документ — план работ, критерии готовности и набор копируемых промптов для последовательной реализации MVP. Перед каждой задачей исполнитель сверяется с планом, изучает текущий код и отмечает фактический результат здесь. План не заменяет проверку репозитория: повторно используй существующие модели, компоненты, API и соглашения, если они уже есть.

## Версия 2.0: границы продукта и принятые решения

Новая концепция заменяет прежнюю модель «один независимый преподаватель» на платформу с одной онлайн-школой и автономными рабочими пространствами преподавателей. Интеграции с внешней школой в MVP нет: Connected — школьное пространство внутри самой платформы.

- **Типы пользователей:** администратор школы, преподаватель, ученик. В первом релизе поддерживается одна школа на инсталляцию и независимые standalone-преподаватели; мультиарендность для нескольких школ не входит.
- **Режимы преподавателя:** один аккаунт может одновременно иметь личное пространство и членство в школе. Данные этих пространств должны быть логически разделены.
- **Школьное пространство:** администратор приглашает преподавателей, управляет общей базой учеников и каталогом курсов, подтверждает регистрацию учеников и назначает их преподавателям. Преподаватель видит только назначенных ему учеников; администратор — всех учеников школы.
- **Standalone:** преподаватель самостоятельно ведёт своих учеников и расписание. Ученик может зарегистрироваться и ожидает подтверждения/привязки преподавателем.
- **Права на финансы:** в школьном режиме финансовые данные назначенного ученика доступны его преподавателю и администратору школы; в standalone — соответствующему преподавателю.
- **Расписание:** занятия создаёт/ведёт преподаватель, в том числе в школьном режиме; школьный курс — общая сущность/категория каталога, не видеохостинг и не LMS.
- **Вход:** в первом релизе email и пароль. Google и Telegram отложены.
- **Уведомления:** отдельные push- и Telegram-напоминания отложены; дашборд остаётся основным местом ежедневных напоминаний.
- **Домашние задания:** ученик отправляет текст, фото и ссылку; преподаватель выставляет числовую оценку 0–100. В текущем объёме нет статуса «Зачёт/Незачёт» и двусторонней ветки комментариев.
- **Два финансовых показателя:** остаток занятий и денежный баланс считаются независимо. Валюта — гривна (UAH). Цена задаётся стандартно для ученика; денежный долг = начисления за проведённые и подлежащие оплате поздние отмены минус зарегистрированные денежные оплаты. Положительное значение — долг, отрицательное — предоплата. Запись оплаты содержит сумму и число оплаченных занятий.
- **Списание занятия:** проведённое занятие списывает одну оплаченную единицу; отмена менее чем за 5 часов до начала тоже списывает единицу и начисляет стоимость, отмена за 5 часов или раньше — нет. Перенос не должен приводить к двойному списанию/начислению.
- **Календарь:** день/неделя/месяц, неделя с понедельника, явная настройка часового пояса, разовые и повторяющиеся еженедельные занятия.
- **Файлы:** поддерживаются текст, фото и ссылки; безопасное хранение изображений и ограничения размера/форматов требуют фиксации в конфигурации.

## Порядок работ и критерии готовности

### Задача 0. Обследование текущего проекта — выполнена

Результаты обследования и исходные ограничения сохранены ниже. Перед дальнейшей работой сверяй найденную архитектуру с обновлёнными требованиями версии 2.0.

### Задача 1. Учётные записи, рабочие пространства и роли

**Зависит от:** задачи 0 и решения по безопасной миграции существующих учётных записей.

**Работы:**
- Заменить небезопасную авторизацию на email/пароль с проверенным хешированием паролей и серверной авторизацией.
- Поддержать администратора школы, преподавателя и ученика; преподаватель может состоять в школьном пространстве и иметь отдельное standalone-пространство.
- Реализовать приглашение преподавателя администратором школы; самостоятельную регистрацию ученика с подтверждением и назначением преподавателя. Для standalone привязку подтверждает преподаватель.
- Обеспечить школьный bootstrap и начальную настройку без публичного обхода авторизации.
- Ограничить все запросы по роли, пространству и назначению ученика на сервере; данные standalone не смешивать с данными школы.

**Готово, когда:** вход/выход и регистрации работают, членство и переключение пространств не дают межпространственного доступа, а API-тесты покрывают роли, назначение и чужие идентификаторы.

### Задача 2. База школы, ученики, каталог курсов и карточки

**Зависит от:** задачи 1.

**Работы:**
- Разделить школьных учеников и личных учеников преподавателя; определить модель назначения ученика одному или нескольким преподавателям.
- Реализовать список, карточку и поиск/фильтрацию учеников с контактами, родителями, заметками, целями и историей реальных занятий.
- Дать администратору школы управление общей базой учеников и назначениями; преподавателю — доступ только к назначенным ученикам.
- Добавить школьный каталог курсов/категорий для фильтрации и связи с заданиями/занятиями; не строить систему размещения видео или полноценную LMS.
- Развести школьные данные, личные заметки преподавателя и standalone-данные согласно правам.

**Готово, когда:** роли видят только положенный им набор данных; список, карточки, назначения, контакты и история работают без дублирующих источников истины.

### Задача 3. Оплаты, стоимость занятий и два баланса

**Зависит от:** задач 1–2.

**Работы:**
- Вести журнал оплат в UAH с датой, суммой и количеством оплаченных занятий.
- Поддержать стандартную стоимость занятия для ученика и определить, как фиксируются изменения тарифа во времени.
- Рассчитывать остаток уроков и денежный долг/предоплату раздельно, опираясь на журнал оплат и финансовые начисления занятий.
- Начислять долг за проведённые и за поздно отменённые занятия; отмена за 5 часов или раньше не списывает занятие и не начисляет сумму.
- Обеспечить транзакционность, аудит корректировок и идемпотентность начислений/списаний.
- В школьном режиме разрешить просмотр финансов назначенного ученика преподавателю и администратору; в standalone — только владельцу-преподавателю.

**Готово, когда:** оба показателя объяснимо рассчитаны, суммы не теряют точность, корректировки сохраняют историю, а тесты покрывают границы и повторные операции.

### Задача 4. Календарь, повторения и статусы

**Зависит от:** задач 1–3.

**Работы:**
- Реализовать календарь день/неделя/месяц, фильтры индивидуальных занятий и курсов, создание занятия и бронирование времени.
- Разрешить преподавателю создавать разовые занятия и повторяющиеся еженедельные серии; использовать школьный каталог курсов.
- Добавить шаблоны расписания в минимальном объёме, если они не дублируют серию повторений; конкретный смысл шаблона уточнить в плане до реализации.
- Поддержать проведено/отменено/перенесено и финансовые последствия из задачи 3.
- Определить поведение при редактировании отдельного занятия серии и всей серии.

**Готово, когда:** календарь корректно работает в выбранном часовом поясе, а переходы статусов не создают повторных начислений и списаний.

### Задача 5. Домашние задания и проверка

**Зависит от:** задач 1–2.

**Работы:**
- Преподаватель создаёт задание для ученика/курса; ученик видит только назначенные ему работы.
- Поддержать отправку текста, ссылок и фото; преподаватель видит очередь, фильтрует по ученику/курсу и выставляет числовую оценку 0–100.
- Реализовать безопасное хранение, проверку типа/размера файла и разграничение доступа к вложениям.
- Двусторонние комментарии и зачёт/незачёт не реализовывать в этом объёме.

**Готово, когда:** весь цикл сдачи и проверки работает, данные и файлы изолированы по ученику/пространству, а оценка корректно сохраняется и отображается.

### Задача 6. Дашборд «Сегодня» и финансовые предупреждения

**Зависит от:** задач 3–5.

**Работы:**
- Показать занятия на сегодня с быстрым изменением статуса.
- Показать счётчик и ленту работ, ожидающих проверки.
- Добавить мини-отчёт о долге/предоплате учеников в рамках разрешений текущего пространства.
- Добавить цветовое предупреждение о низком остатке оплаченных занятий.
- Обработать пустые состояния, загрузку и ошибки без фиктивных данных.

**Готово, когда:** дашборд показывает согласованные с расписанием/проверкой/финансами данные и предоставляет быстрый доступ к ежедневным действиям.

### Задача 7. Сквозная проверка, интерфейс и эксплуатационная документация

**Зависит от:** задач 1–6.

**Работы:**
- Проверить standalone и школьные сценарии, приглашение преподавателя, регистрацию/назначение ученика и разграничение доступа.
- Проверить оплату, оба баланса, отмену ровно на границе 5 часов, повторения, сдачу задания и дашборд.
- Проверить миграции на отдельной чистой тестовой БД, Docker Compose, адаптивность и обработку ошибок.
- Обновить README: запуск, первичный bootstrap школы, создание standalone-аккаунта, роли, конфигурация файлов, денежные правила и известные ограничения.

**Готово, когда:** подтверждённые сценарии и проверки записаны, незапущенные проверки явно обозначены, инструкции позволяют воспроизвести запуск без предположений.

### Результаты обследования (задача 0)

**Карта текущей архитектуры**

- Frontend: React 19 / Create React App, точка входа [frontend/src/index.js](frontend/src/index.js), `BrowserRouter` и маршруты в [frontend/src/App.js](frontend/src/App.js): `/`, `/about`, `/login`, `/admin`, `/teacher`. Фактически реализованы информационная страница, форма входа, экран расписания администратора и экран расписания преподавателя. Общего API-клиента/сервисного слоя нет: компоненты вызывают `fetch` непосредственно; базовый URL задаётся в [frontend/src/api.js](frontend/src/api.js).
- Сценарий входа: [LoginForm.js](frontend/src/components/MainContent/LoginForm/LoginForm.js) отправляет `login/password` на `POST /api/auth/login` и сохраняет JWT, роль и `teacherId` в `localStorage`. [ProtectedRoute.js](frontend/src/routers/ProtectedRoute.js) проверяет только наличие токена и сохранённую в браузере роль. Экран преподавателя запрашивает `GET /api/teachers/{id}`; экран администратора получает список через `GET /api/teachers`, добавляет слот через `POST /api/teachers/{id}/lesson` и удаляет через `DELETE /api/teachers/{teacherId}/lesson/{lessonId}`.
- Backend: ASP.NET Core 9 контроллеры напрямую используют [AppDbContext.cs](backend/Data/AppDbContext.cs); отдельного бизнес-сервисного слоя и backend test-проекта в репозитории нет. [AuthController.cs](backend/Controllers/AuthController.cs) проверяет login и пароль сравнением строк в БД и выдаёт JWT на два часа. [TeachersController.cs](backend/Controllers/TeachersController.cs) возвращает список/одного преподавателя с уроками и выполняет добавление/удаление уроков.
- Данные: [Teacher.cs](backend/Models/Teacher.cs) имеет коллекцию `Lessons`; [Lesson.cs](backend/Models/Lesson.cs) хранит день, начало, конец и название строками, а связь `Lesson.TeacherId` → `Teacher` задана внешним ключом с каскадным удалением. [User.cs](backend/Models/User.cs) хранит `Login`, `Password`, `Role`, nullable `TeacherId`; EF-связь/внешний ключ `User.TeacherId` не настроены. Моделей учеников, контактов, оплат, списаний, заданий, отправок и файлов не найдено.
- EF Core / SQL Server: цепочка миграций начинается с таблиц `Teachers`, `Users`, `Lessons`; последующие миграции добавляют seed-данные пользователей/преподавателей (одна миграция seed-пользователей пуста). Снимок модели содержит те же seed-аккаунты. [Program.cs](backend/Program.cs) берёт SQL Server connection string из конфигурации и автоматически вызывает `Database.MigrateAsync()` при старте.
- Запуск: [docker-compose.yml](docker-compose.yml) поднимает SQL Server 2022, API и React; SQL хранится в сохраняемом томе `sql_data`, порт SQL публикуется на хост. API получает строку подключения через переменные окружения, frontend URL API — через build/runtime `REACT_APP_API_URL`. [frontend/README.md](frontend/README.md) документирует `docker compose up --build`, остановку через `docker compose down`, а также `npm ci`, `npm start`, `npm test -- --watchAll=false` и `npm run build` для frontend.
